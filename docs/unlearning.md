# What I Unlearned While Building Driftline

The largest change was not that I wrote less code. It was that I stopped treating authorship—or an AI’s confidence—as evidence that the work was right.

My default habit is to begin once the happy path sounds plausible and postpone awkward cases until the interface feels real. For Driftline, I reversed that sequence. Before implementation, I made “stalled,” “priority,” and “done” falsifiable. I asked AI to attack the rules, propose incompatible alternatives, and generate hostile data. Then I checked those proposals with hand calculations, invariants, automated tests, and browser behavior. The useful loop became **Direct → Generate → Falsify → Decide → Record**. AI widened the search; it did not get to declare its own output correct.

I also unlearned that AI-first must mean AI inside the shipped product. Driftline’s runtime is deterministic and uses no external model or API. AI helped shape the schema, compare scoring approaches, generate edge cases, draft implementation, and critique the result. Keeping it out of the runtime made the user-facing decision reproducible: the same CSV, as-of date, and base limit produce the same queue. In hiring, that matters. Fluent generated language can make a weak inference sound authoritative, so every Driftline explanation comes from validated facts and a fixed template.

A second habit I challenged was trusting a believable expected result. My first fixed-sample test failed because I expected seven distinct owners while the program reported six. It was tempting to “fix” the code. Inspecting the nine flagged rows showed the implementation was right: repeated owners had been double-counted in my mental tally. I corrected the oracle, not the algorithm, and kept the failed test in the log. A red test proves disagreement; it does not tell me which side deserves trust.

The browser exposed a different class of failure. The sentence “against a 11-day limit” passed every arithmetic check and still damaged credibility. A common local port was also captured by an old service worker from another app, so a successful HTTP response was not enough to prove the intended page was on screen. I changed the wording, moved the server to port 8765, and verified the visible title and workflow. Function correctness and human trust are related, but they are not interchangeable.

I changed what “raising the load” meant. At first I associated difficulty with more features. Here the harder move was to increase the burden of proof: stage-aware limits instead of one universal number, an inclusive threshold, overdue commitments without invented blame, duplicate quarantine, stable ties, prohibited-field invariance, formula-safe export, sensitivity analysis, and a 10,000-row check. Some tempting features were deliberately cut. There is no ATS sync, automatic messaging, holiday calendar, persistence, or production security claim. Automated mobile viewport testing was unavailable, so I documented that limit rather than translating responsive CSS into a claim of verified mobile behavior.

I also unlearned that useful automation must remove the human. Driftline organizes attention; it does not judge people, send a follow-up, or change a hiring record. Names identify rows but do not affect priority. The process-debt metric describes workflow backlog, not candidate worth or recruiter performance. The user can inspect the stage, dates, effective limit, score components, explanation, and proposed action before deciding what to do.

This build was compressed into five deliberate work passes on one calendar day, and the log says so. Seventeen tests pass; the default sample reconciles; browser interactions and export were checked; and 10,000 rows processed in roughly 28 milliseconds on the build machine. None of that makes Driftline production-ready. What I unlearned is that speed and rigor are not opposites. AI can make the loop faster and broader, but every important claim still has to earn its place through evidence.
